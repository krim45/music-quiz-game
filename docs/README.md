# docs

이 디렉터리가 기획·정책·아키텍처의 **단일 원본**이다. 코드와 같은 커밋에서 바뀌고,
git이 버전 히스토리를 갖는다. 외부 도구(노션 등)에 복사본이 있다면 그건 읽기용 미러다.

## 디렉터리

| 경로 | 담는 것 | 판별 기준 |
|---|---|---|
| `product/` | 기획 — 무엇을 만드는가 | 사용자에게 보이는 기능·화면·흐름 |
| `policy/` | 정책 — 어떤 규칙으로 동작하는가 | 점수, 판정, 권한처럼 "숫자와 조건"이 있는 것 |
| `arch/` | 아키텍처 — 어떻게 구현했는가 | 코드에서 역추출 가능한 사실 |
| `adr/` | 결정 기록 — 왜 그렇게 했는가 | 되돌리기 어렵고 이유가 코드에 안 남는 선택 |

`handoff.md`는 위 어디에도 안 들어간다. 진행 중 컨텍스트라 수명이 짧다.

## frontmatter

모든 문서는 아래로 시작한다. **파일명에 버전을 넣지 않는다** (`spec-v2.md` 금지).
개정 이력은 git이 갖고 있고, 문서는 항상 현재 상태만 서술한다.

```yaml
---
title: 점수 정책
status: draft | active | deprecated
updated: 2026-09-20
---
```

`version`은 **깨지면 남이 아픈 계약 문서에만** 붙인다 — 소켓 프로토콜, REST API,
저장된 데이터의 해석이 달라지는 게임 룰. semver를 따르고, breaking change면 major를 올린다.
순수 기획 문서는 `status`와 `updated`만으로 충분하다.

`deprecated`로 바꿀 때는 파일을 지우지 말고 `superseded_by: <경로>`를 추가한다.

## 쓸 때

- **없으면 실제로 막히는 것만 쓴다.** 완성도보다 "다음 작업을 시작할 수 있는가"가 기준이다.
- AS-IS(`arch/`)와 TO-BE(`product/`, `adr/`)를 한 문서에 섞지 않는다.
  섞이면 몇 달 뒤에 어디까지 구현된 건지 알 수 없게 된다.
- 코드와 문서가 어긋나면 **코드가 맞다.** 문서를 고치거나, 코드가 틀렸다면 ADR을 남기고 고친다.
